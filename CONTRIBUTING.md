# Contributing to CeloHT Documentation

Thank you for helping build documentation worthy of CeloHT's mission. This repository is community-governed — see [GOVERNANCE.md](./GOVERNANCE.md).

## Language Policy

All content in this repository is written in **English**. This is the reference documentation for the global developer, partner, and governance community. (Direct community education materials in Haitian Creole live in the Education Working Group's separate content pipeline — see [EDUCATION.md](./EDUCATION.md#localization).)

## What You Can Contribute

- Corrections, clarifications, or updates to existing documents
- New documentation filling a genuine gap (propose via issue first)
- Diagrams, examples, or tables that improve clarity
- Translations of this documentation into additional reference languages (French is the current priority)

## Standards for Every Document

- **Complete.** No "TODO," no placeholder sections, no "coming soon" left unexplained.
- **Cross-linked.** Reference related documents using relative links, and add a `## References` section where relevant.
- **Structured.** Follow the standard structure used across this repository: Purpose/Scope → Overview → Detail sections → References → (Version History via CHANGELOG.md).
- **Accurate.** Technical claims (API behavior, contract logic) must match the actual specification/implementation — if you're documenting something not yet built, mark it clearly as planned/specification-stage, as done in [SMART_CONTRACTS.md](./SMART_CONTRACTS.md) and [DAPP.md](./DAPP.md).
- **Consistent with the No-Token Policy.** Never introduce language implying investment, returns, or token existence. See [NO_TOKEN_POLICY.md](./NO_TOKEN_POLICY.md).

## Elevated Review Requirements

Changes to the following require two-maintainer approval, per [GOVERNANCE.md](./GOVERNANCE.md#decision-making-process):

- [NO_TOKEN_POLICY.md](./NO_TOKEN_POLICY.md)
- [GOVERNANCE.md](./GOVERNANCE.md)
- [LEGAL_STATUS.md](./LEGAL_STATUS.md)
- Non-affiliation disclaimer wording anywhere it appears

## How to Propose a Change

1. Open an issue describing the gap or correction
2. For new documents, get initial maintainer feedback before writing the full draft — this avoids wasted effort on scope that doesn't fit
3. Submit a PR referencing the issue, following the [PULL_REQUEST_TEMPLATE](./.github/PULL_REQUEST_TEMPLATE.md)
4. A maintainer reviews for accuracy, completeness, and consistency with linked documents

## Documentation Structure Reference

New documents should follow this section order where applicable: Purpose/Scope, Overview, Core content sections, Do's/Don'ts or examples where relevant, References, and rely on [CHANGELOG.md](./CHANGELOG.md) for version history rather than an in-document changelog.
